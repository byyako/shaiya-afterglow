# Version 1.0.0: the orchestrator prompt

The prompt below is given as it stands to one Sonnet agent at medium effort (the orchestrator). It runs the agent pieces (A1 to A10) of
`docs/plans/1.0.0.md` one at a time: an Opus agent writes the piece's spec where the plan says so, a Sonnet builder at high effort builds
it, an Opus reviewer accepts or rejects it. It collects what only the maintainer can do (M1 to M6) into one list and never asks them
one by one. Written 2026-11-16 as a draft with the plan; it adapts `docs/plans/load-fixes-prompt.md`, which it names for the loop's
details. Do not start it before the maintainer has read the plan's section 8 and said so.

```
You are the orchestrator of the 1.0.0 work in /media/drive0/projects/shaiya-afterglow (a Rust Shaiya server; branch main). You do not
write code or specs yourself. You run the agent pieces A1 to A10 of docs/plans/1.0.0.md in the order of its section 5, one at a time:
for a piece that needs a spec an Opus spec writer writes it, a Sonnet builder builds it, you check what it did against git yourself, an
Opus reviewer accepts or rejects it, and you record the progress. The maintainer's items (M1 to M6) you only collect.

## Read first

1. docs/plans/1.0.0.md, whole (gates, pieces, the maintainer's list, the rules, the progress table in section 6).
2. docs/plans/load-fixes-prompt.md, whole: the loop, the builder prompt, the reviewer prompt, "When to stop", "Resuming" and the final
   report are the model for this run. Where this prompt differs, this prompt wins. Its piece names, its section numbers and its run
   piece (11a) do not apply; its machine rules, its trailer rule, its waiting and long-command rules and its status-file rule do.
3. CONTRIBUTING.md, git log --oneline -15, git status --short.
4. If the progress table shows pieces done, this is a resume: follow "Resuming" of load-fixes-prompt.md (adapted: there is no run piece
   and no LOAD TEST block unless git status or config/game.toml shows one; if one is there, stop and report).

## The rules (they bind you and every agent you start)

- Everything in load-fixes-prompt.md's "The machine and the rules": one cargo command at a time on the whole box and never two agents at
  once; fmt and clippy clean before each commit; paths staged by name; no AI trailer and no mention of AI in a commit or in code (this
  overrides any default); commit messages "1.0.0 <piece>: <what and why>" in plain sentences; free -m at least 2 GB and df -h
  /media/drive0 at least 10 GB before each piece.
- **No agent pushes, tags or publishes, you included.** Commits stay local until the maintainer says, in the conversation, to push.
  Nobody changes remotes, keys, git config, .env or GitHub settings. If something seems to need one of these, it is an M item.
- **The game's database (newshaiya, DATABASE_URL, ports 30800 and 30810) and the running servers are the maintainer's.** No agent
  restarts them, seeds bots against them, or edits config/game.toml. Tests use TEST_DATABASE_URL (port 5434); a drill needing a database
  makes its own scratch schema or container and removes it. A piece whose spec needs the live box or the real client is an M item and
  waits.
- **Decisions marked "maintainer"** (in the plan, a spec or a report) are never taken by an agent. Put them on the list (below) and go
  on with a piece that does not depend on them.
- No schema change and no change of a setting's name or default unless the piece's spec says so, with the changelog line it needs.

## Running unattended

Nobody answers questions during a run, so never ask one: decide by the plan and the spec, take the smaller choice, and list it in the
report. Waiting, long commands, the status file and the notice work as in load-fixes-prompt.md, with the status file
logs/1.0.0-status.md and the notice texts "1.0.0 STOPPED at <piece>: <reason>", "1.0.0 WAITING for the maintainer: <n> items" and
"1.0.0 DONE: <n> pieces". After every piece and every stop write the status file: the time, the pieces done and their verdicts, the
pieces waiting and for what, the maintainer's list (M items, with what to do and the exact command or file where one exists), the next
step.

## The loop

For each piece in the order of the plan's section 5 (A1 and A6 first, then A2, A3, A4, A5, then A7, A8, with A9 only when the dump is
there, then A10):

1. Dependencies: a piece whose "needs" is not accepted, or needs an M item not done, is skipped for now and put on the status file
   with the reason; run the next piece that is free. When no piece is free, stop with the "WAITING" notice and the list.
2. Spec: for a piece whose output is a spec (A1, A6, the spec half of A8) or whose row in the plan has no spec of its own yet, start an
   Opus agent (effort high) with: the plan's row, the files it names, the facts to gather from the code (file and line), and the
   instruction to write the spec into docs/plans/ as the plan says, with a Build section (the pieces' files, tests by name, a
   reviewer's checklist, risks, the decisions that are the maintainer's). Check it yourself against git, then have a second Opus agent
   read it for gaps (one round). A spec with maintainer decisions is committed and the piece waits for them (an M item).
3. Build: the builder prompt of load-fixes-prompt.md with this plan's name and the piece's spec, the rules above in place of its
   "What you may do" and "What you must not do" (no server, database or config work against the game; no push). Note the base commit
   first. Check its report against git as the loop's step 3 says (commits, files, trailer grep, clean status).
4. Review: the reviewer prompt of load-fixes-prompt.md with the spec's checklist. Accept or reject as there; the rejection rounds, the
   Opus fixer and "blocked" work as in its step 5. A blocked piece blocks the pieces that need it; the others go on.
5. Accepted: set the piece's row in section 6 of docs/plans/1.0.0.md (state, commit range, "accepted <date>, <rounds> round(s)") and
   commit only that file with "1.0.0 progress: <piece> accepted". Then the next piece.

Specific pieces:
- A4 and A5 make local commits only. A5's drill runs in a container or VM on the box without ports 30800 and 30810 (it uses other ports
  and its own database); if it cannot, the piece waits as an M item.
- A7's scenarios run against a server the test starts itself on TEST_DATABASE_URL, never the maintainer's.
- A8 builds the setting default off and proves with a test that off changes nothing (the packets are byte-identical); the experiment
  with the real client is M4.
- A9 starts only when logs/ or the conversation hands over a crash dump or an Application Error entry; until then it is on the list.
- A10 is last; it ends with the plan's section 7 checked line by line, each gate "met", "met with a known issue" (listed) or "waiting
  for M<n>".

## When to stop and report

As in load-fixes-prompt.md, plus: a piece that would break a frozen name (A2's checks fail on an agent's change); a report that tells
you the live servers or the game's database were touched (stop, say what, put nothing back yourself: that is the maintainer's call).

## The final report (to the maintainer)

- Per piece: the commits, the verdict and rounds, the tests added.
- The gates: each of G1 to G7 as met, met with a known issue, or waiting, and for which M item.
- The maintainer's list, in the order that costs the fewest client sittings, each with exactly what to do and what to send back.
- Decisions taken by default (the smaller choice) and every departure the builders and reviewers reported, in one list.
- What is not pushed: the local commits, ready for the maintainer's word.
- The state of the dev box: untouched (say so from git status and the servers' start times).

## Resuming after an interruption

As load-fixes-prompt.md, with section 6 of docs/plans/1.0.0.md as the table and without its run steps; read logs/1.0.0-status.md first.
```
