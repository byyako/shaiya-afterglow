# Version 1.0.0: the plan (draft 2026-11-16)

**Status: a draft for the maintainer's review. No agent has been started.** 1.0.0 means the settings, the database and the extension
API stop breaking, and a new operator's first hour (install, log in, play, relog) works with the real client. This page says what that
takes, which parts agents can do without the maintainer, and which parts only the maintainer (the real client, GitHub, decisions) can.

Background: the load runs of 2026-11-14 and 2026-11-15 (`docs/testing/load-pvp.md`, `docs/testing/maps-lock-investigation.md`) show the
server holds 700 bots on the dev box. The real client crashed at 300 players in view (2026-11-12) and at about 490 (2026-11-15, twice);
the server side was healthy each time. The cause is not known.

## 1. The gates

| gate | what | who can do it |
|---|---|---|
| G1 | Release 0.4.0 (pets, the extensions split) | agents prepare; the maintainer creates the extensions repository, tests with the client, approves the tag |
| G2 | The smoke list walked with the real client (work item A3) | the maintainer walks; agents automate what needs no eyes and fix failures |
| G3 | A fresh-machine install drill | agents in a container or VM; the maintainer for the real-client login |
| G4 | The long checklist (`docs/testing/live-test-checklist.md`) | mostly the maintainer; agents sort and automate the bot-checkable part |
| G5 | The client crash with many players in view | the maintainer gives a crash dump; agents analyse the client and build a view cap |
| G6 | Stability freeze (settings, schema, extension API) with an upgrade path | agents; the maintainer decides what is frozen |
| G7 | Release polish (changelog, docs, deviations, security pass) | agents |

Out of 1.0.0 unless the maintainer says otherwise: the web API (B1), operations for a public server (B2), converting an existing
original server, the balance project.

## 2. Roles and rules

One orchestrator (Sonnet, medium), builders (Sonnet, high), a spec writer and a reviewer for each piece (Opus). The orchestrator writes
no code; it runs the pieces in order, checks each builder's work against `git` itself, has an Opus reviewer accept or reject it, and
keeps the progress table (section 6) and `logs/1.0.0-status.md` current. The rules of `docs/plans/load-fixes-prompt.md` apply as they
stand (one cargo command at a time on the box, never two agents at once, fmt and clippy clean, paths staged by name, no trailers, the
long-command and waiting rules, "one more round" for a rejected piece). Changes for this run:

- **No agent pushes, tags or publishes.** Commits stay local. The pushes and the tags are the maintainer's, or the orchestrator's after
  the maintainer says so in this conversation. Builders never touch remotes, keys, git config, or GitHub settings.
- **The dev box is shared with the game.** A piece that restarts a server or changes the database says so in its spec; a piece that
  needs the real client waits for the maintainer (section 4). The live server's database (`newshaiya`) is never a test target; tests
  use `TEST_DATABASE_URL`.
- **Decisions the spec marks "maintainer"** are not taken by an agent: the piece stops there and the question goes on the list in
  section 4.

## 3. Pieces an agent can do (phase A, no maintainer needed)

Order: the spec pieces first (Opus), then the builds, each build reviewed before the next starts.

| piece | gate | what | output | needs |
|---|---|---|---|---|
| A1 | G6 | **Stability inventory** (Opus): list every setting name (`docs/server/settings.md`, `game-server config`), every table and column the server reads or writes (`db/migrations`), the extension API (`extension.toml`, rule points, effects, Lua `game.*`), the packet and save formats an operator's data depends on. Propose what is frozen, what may change in 1.x, what is removed before 1.0 (renames and cleanups done now, once). | `docs/plans/stability.md` with a table and a list of maintainer decisions | |
| A2 | G6 | **Freeze checks** (builder): a test that fails when a setting name, a migration already released, an extension rule point or a Lua function changes without the changelog saying so; a snapshot of each. | tests + `docs/server/stability.md` | A1 signed off by the maintainer |
| A3 | G6 | **Upgrade path**: a database from the last released version (v0.3.0) upgraded to 1.0 by the migrations and the setup's upgrade step, on a scratch schema; the drill written and run; the downgrade stated (restore from backup). | a drill script, `docs/server/upgrade.md` | A2 |
| A4 | G1 | **0.4.0 release prep**: version bump from `0.4.0-dev`, the changelog's date, `release.yml` read through for the tag, the extensions repository as a local folder complete (README, version, `ext lint` clean), the pets rehearsal on a drill database (`docs/plans/ext-4-pets.md`). | commits + a list of what the maintainer does | |
| A5 | G3 | **Fresh-install drill in a container**: a clean image, `tools/setup.sh` from the release tarball, the servers up, a bot logging in and playing (`bot probe`), a relog. Reports what the README's quick start gets wrong. | a drill script, fixes, a result in `docs/plans/install.md` | A4 |
| A6 | G2, G4 | **Sort the checklist** (Opus): every item of `live-test-checklist.md` as bot-checkable or client-only; for the bot-checkable ones, which packets and database rows prove the result. | a table in `docs/testing/live-test-solo.md` | |
| A7 | G2, G4 | **Bot scenarios** (builder): the bot-checkable items as `bot scenario` tests (login, move, fight, loot, shop, warehouse, relog, trade between two bots, party, duel), run as a command, results written to the checklist page's JSON as "bot-checked" (not "seen"). | tests, `docs/testing/` updated | A6 |
| A8 | G5 | **View cap** (Opus spec, builder): a setting (default off, the original's behaviour) that limits how many players one client is sent in view (the nearest N), the rest left out until they come near; bots check that fights and visibility stay consistent. | A9 | G5 | **Crash analysis** (Opus, REA tools): from the maintainer's dump or Event Viewer entry, find the faulting function in the client binary and say what state it needs. | `docs/client/crash-many-in-view.md` | the dump (M3) |

## 4. What only the maintainer can do (phase M, collected in one list)

Agents never ask these one at a time; the orchestrator keeps the list in `logs/1.0.0-status.md` and the maintainer takes them in one sitting.

| item | gate | what |
|---|---|---|
| M1 | G1 | Create `shaiya-afterglow-extensions` on GitHub and say when it is there; approve the push and the 0.4.0 tag |
| M2 | G1, G2, G4 | Client sittings: the pets test with client patch 111, the smoke list (two clients for trade), and the checklist items A6 marks client-only (the sittings in `live-test-solo.md`) |
| M3 | G5 | Crash dump or Application Error entry (faulting module and address) from the next crash at about 300 in view; also the time and what was on screen |
| M4 | G5 | The experiment: with `view cap` on at 200, 300 and 500 bots, does the client still crash? Which N? |
| M5 | G3 | One real-client login against the fresh install of A5 |
| M6 | G6 | The decisions in `stability.md` (what is frozen) and the 1.0.0 push and tag |

## 5. Order

1. A1 (spec) and A6 (sort), in parallel with nothing else on the box; the maintainer reads A1's decision list (M6, first part).
2. A2, A3, then A4, A5 (builds, one at a time, each reviewed).
3. A7, then A8 (the view cap), with the maintainer's M3 and M4 as soon as a client sitting is possible; A9 when the dump is there.
4. M1, M2, M5 in one or two client sittings, using the list the orchestrator has kept.
5. A10, then the 1.0.0 tag (M6).

## 7. Done when

Every gate's line in section 1 is met: G1 the tag 0.4.0 exists; G2 the smoke list is walked and each failure is fixed or listed;
G3 the fresh-install drill passes in a container and once with the real client; G4 no checklist item is known failing, or each is a
listed known issue; G5 the crash is understood and either fixed, or documented as a client limit with the view cap as the setting; G6
the freeze checks run in CI and the upgrade from v0.3.0 is drilled; G7 the changelog, docs and security pass are done. Then the
maintainer tags 1.0.0.

## 8. Open questions for the maintainer

1. Is the web API (B1) or the conversion of an existing original server part of 1.0.0? This plan says no.
2. Is a documented client limit with an optional view cap acceptable for G5 if the crash can't be fixed?
3. How strict is G4: every checklist item green, or "no known failure, the rest listed"? This plan says the second.
