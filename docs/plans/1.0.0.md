# Version 1.0.0: the plan (draft 2026-11-16, scope decided the same day)

**Status: scope decided by the maintainer (section 8); no agent has been started.** 1.0.0 means the settings, the database and the extension
API stop breaking, and a new operator's first hour (install, log in, play, relog) works with the real client. This page says what that
takes, which parts agents can do without the maintainer, and which parts only the maintainer (the real client, GitHub, decisions) can.

Background: the load runs of 2026-11-14 and 2026-11-15 (`docs/testing/load-pvp.md`, `docs/testing/maps-lock-investigation.md`) show the
server holds 700 bots on the dev box. The real client crashed at 300 players in view (2026-11-12) and at about 490 (2026-11-15, twice);
the server side was healthy each time. The cause is not known.

## 1. The gates

| gate | what | who can do it |
|---|---|---|
| G1 | Release 0.4.0 first (the extension system and the extensions split; the extensions' own releases are theirs) | agents prepare; the maintainer creates the extensions repository and approves the tag |
| G2 | The smoke list walked with the real client (work item A3) | the maintainer walks; agents automate what needs no eyes and fix failures |
| G3 | A fresh-machine install drill | agents in a container or VM; the maintainer for the real-client login |
| G4 | The long checklist (`docs/testing/live-test-checklist.md`) | mostly the maintainer; agents sort and automate the bot-checkable part |
| G5 | The client crash with many players in view | the maintainer gives a crash dump; agents analyse the client and build a view cap |
| G6 | Stability freeze (settings, schema, extension API) with an upgrade path | agents; the maintainer decides what is frozen |
| G7 | Release polish (changelog, docs, deviations, security pass) | agents |
| G8 | **Moving an existing original server to Shaiya Afterglow** (its definitions, world files and players), and the original's behaviour recreated | agents spec and build; the maintainer's original server files and decisions (it was to be "fully discussed before it is specified", `ideas.md` section 5) |

The client is the stock EP4.5 client (US `game.exe`, 2010-04-26, patch 108), with the optional `fixes.dll` for extra features.

Out of 1.0.0: the web API (B1, version 1.x), operations for a public server (B2), the balance project, the pets (extension work, not
core: they ship with the extensions repository, not with the server's release).

## 2. Roles and rules

One orchestrator (Sonnet, medium), builders (Sonnet, high), a spec writer and a reviewer for each piece (Opus). The orchestrator writes
no code; it runs the pieces in order, checks each builder's work against `git` itself, has an Opus reviewer accept or reject it, and
keeps the progress table (section 6) and `logs/1.0.0-status.md` current. The rules of `docs/plans/load-fixes-prompt.md` apply as they
stand (one cargo command at a time on the box, never two agents at once, fmt and clippy clean, paths staged by name, no trailers, the
long-command and waiting rules, "one more round" for a rejected piece). Changes for this run:

- **No agent pushes, tags or publishes.** Commits stay local. The pushes and the tags are the maintainer's, or the orchestrator's after
  the maintainer says so in this conversation. Builders never touch remotes, keys, git config, or GitHub settings.
- **The dev box is shared with the game.** A piece that restarts a server or changes the database says so in its spec; a piece that
  needs the real client waits for the maintainer (section 4). The live server's database (`newshaiya`) is never a test target; tests
  use `TEST_DATABASE_URL`.
- **Decisions the spec marks "maintainer"** are not taken by an agent: the piece stops there and the question goes on the list in
  section 4.

## 7. Done when

Every gate's line in section 1 is met: G1 the tag 0.4.0 exists; G2 the smoke list is walked and each failure is fixed or listed;
G3 the fresh-install drill passes in a container and once with the real client; G4 no checklist item is known failing, or each is a
listed known issue; G5 the crash is understood and either fixed, or documented as a client limit with the view cap as the setting; G6
the freeze checks run in CI and the upgrade from v0.3.0 is drilled; G7 the changelog, docs and security pass are done. Then the
maintainer tags 1.0.0.

## 8. Decisions (the maintainer, 2026-11-16)

1. **Scope.** The web API is 1.x. Converting an existing original server and recreating the original's behaviour are part of 1.0.0 (G8).
2. **The crash (G5).** The maintainer investigates the client with `docs/testing/client-crash-prompt.md`; A8 and A9 follow its answer.
3. **Checklist strictness (G4).** "No known failing item, the rest listed as known issues", not every item green.
4. **The freeze (G6).** Agreed 2026-11-16: setting names and defaults, released migrations, and the extension API (`extension.toml`, rule points, item effects, Lua `game.*`) are frozen from 1.0.0; a renamed setting keeps its old name with a warning for a deprecation period. Not frozen: game-behaviour fixes, packet internals, log text. A1 lists the candidates for cleanup before the freeze.
5. **Order.** 0.4.0 first, then 1.0.0.
6. **Extensions repository.** Meant to exist already; it does not (M1).
7. **Client sittings.** A small test, optionally with bots; pets are not core (G1, M2 changed).
8. **Checklist coverage (G4).** Walked as far as possible through code and bots (A6, A7); what needs eyes is listed for live testing.
9. **The client.** Stock EP4.5 with the optional `fixes.dll`.
